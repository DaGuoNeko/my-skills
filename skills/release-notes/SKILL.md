# 版本发布更新日志工作流

当用户要求发布新版本、写更新日记、生成更新日志时，按以下步骤执行。

## 一、收集更新内容

1. 向用户确认本次版本号（如 3.6.0）和上一版本号（如 3.5.8）
2. 向用户确认本次所有更新条目和修复条目
3. 如果用户直接给出了条目列表，直接使用

## 二、条目排序规则

按以下顺序整理：
1. **更新**条目在前（新功能、优化、改动）
2. **修复**条目在后（bug修复）

保持用户原始措辞，不做过度改写，仅做格式统一。

## 三、定位帮助界面文件

### 搜索方法

在项目 `custom_attrR/ui/` 或对应的资源包 `ui/` 目录下，搜索包含上一版本号（如 `3.5.8`）的 JSON 文件：

```bash
grep -rn "<上一版本号>" <项目路径>/ui/ 2>/dev/null
```

如果找不到，搜索 `更新日记` 或 `更新日志` 或 `Help_pass` 关键词：

```bash
grep -rln "更新日记\|更新日志\|Help_pass" <项目路径>/ui/ 2>/dev/null
```

### 确认结构

找到文件后，阅读上一版本条目附近的代码，确认：
- 版本条目的 key 命名规则（如 `Help_pass(2w3.5.8)` 中的前缀 `2w`）
- 文本条目的 key 命名规则（如 `Help_Text(ti53.5.8)` 中的前缀 `ti5`）
- `$pass_text` 的格式（是否带 `(最近更新)` 后缀）
- `$help_text_name` 的内容格式（换行符风格、分类方式）

不同项目可能使用不同的命名前缀和格式，以实际代码为准。

## 四、写入帮助界面更新日记

### 插入新版本条目

在上一版本条目**前面**插入新版本，参照已有的条目格式。通用模板：

```json
{
    "<Help_pass key命名><新版本号>@<命名空间>.Help_pass": {
        "$pass_text": "<新版本号>版本的更新与修复(最近更新)",
        "layer": 1
    }
},
{
    "<Help_Text key命名><新版本号>@<命名空间>.Help_Text": {
        "$help_text_name": "更新:\n1. 条目一\n2. 条目二\n\n修复:\n1. 修复条目一\n2. 修复条目二"
    }
},
```

**关键**：key 命名、命名空间、控件模板名都必须参照该项目已有条目的实际写法，不要假设固定值。

### 修改旧版本标记

把上一版本的 `$pass_text` 中的 `(最近更新)` 去掉。

### 注意事项
- `$help_text_name` 中用 `\n` 换行，更新条目和修复条目之间用 `\n\n` 分隔
- 更新条目前加 `更新:\n`，修复条目前加 `修复:\n`（如果项目已有条目用的是其他分类标题，保持一致）
- 每条以序号开头（1. 2. 3.）
- 如果项目已有条目不带分类标题（直接列序号），则保持该项目的风格

### 验证
写入后验证JSON合法性：
```bash
python -c "import json; json.load(open('<文件路径>', encoding='utf-8')); print('JSON OK')"
```

## 五、生成纯文本更新日志

在回复中输出一份排好序的纯文本，格式如下，方便用户直接复制：

```
<新版本号> 更新内容

【更新】
- 条目一
- 条目二

【修复】
- 修复条目一
- 修复条目二
```

## 六、提交git

1. `git add` 暂存所有相关改动文件（排除 `studio.json`、`.zcode/` 等非功能文件）
2. `git commit` 提交，commit message 格式：`正式版 <新版本号>` 或用户指定的格式
3. commit message body 中按更新/修复分类列出条目摘要

## 七、完成确认

提交后告知用户：
- commit hash
- 提交了哪些文件
- 哪些文件未提交（如 studio.json）
