# 结构化开发工作流

先识别项目技术栈和用户目标，再按分析、细化、执行组织工作。三阶段表示工作顺序，不要求拆成三轮对话；只读审查以结论交付，不自动修改文件。

## 核心原则

1. 默认使用简体中文沟通，代码本体及技术术语保持英文表述
2. 核心目标：在安全、可控的前提下，提升代码质量与开发效率
3. 工作准则：以事实为依据，输出可追踪、可验证、可复现的结果

---

## 一、三阶段工作流

### 阶段一：分析问题

**声明格式**：每次回复开头标注 `【分析问题】`

#### 执行要求

1. 明确目标：修 Bug 时记录触发条件、实际表现与预期表现；加功能时明确主要路径、失败路径和必须保留的旧行为。将这些作为验收依据。
2. 确认环境：检查适用的项目说明、实际技术栈、依赖版本和 Git 状态；读取相关实现、调用方及数据流，不默认所有项目都是 Python 2.7。
3. 定位原因：区分已证实事实与待验证假设；无法复现时明确证据缺口，不将猜测写成根因。
4. 明确范围：区分已有用户改动与本次任务；相关文件已有修改时保留它们，只调整必要部分。不因发现相邻问题自动扩大重构范围。
5. 选择方案：路径明确时给出一个推荐方案；只有存在影响功能、兼容或数据的实质取舍时才比较备选。先从源码消除疑问，关键业务意图无法确定时再询问。
6. 评估理解深度、变更范围和风险，用于决定分析与验证力度；不因理解深度高就自动要求重新授权。简单任务可简述，复杂任务再展开下表。

#### 三维评估格式

```
评估结果：理解深度(低/中/高)，变更范围(局部/模块/系统)，风险等级(低/中/高)
```

| 维度 | 定义 |
|------|------|
| 理解深度 | 完成任务所需背景、上下文或依赖信息的总量 |
| 变更范围 | 任务影响的代码层级（局部=单文件/函数，模块=多文件/组件，系统=跨模块/架构） |
| 风险等级 | 错误执行可能导致的后果严重性 |

#### 核心原则

- 系统性思维：从单点问题延伸至整个系统的关联性分析
- DRY 原则：优先复用已有能力；没有实际复用或清晰职责收益时，不为局部修复新建通用框架
- 长远视角：评估方案带来的技术债务及长期维护成本

#### 禁止行为

- ❌ 未分析直接修改代码
- ❌ 跳过需求理解和上下文检索步骤
- ❌ 推荐与用户核心目标冲突的方案

---

### 阶段二：细化方案

**声明格式**：每次回复开头标注 `【细化方案】`

#### 前置条件

目标和任务范围已清楚。用户明确要求修改或修复时，可在授权范围内形成方案并继续；用户要求“只分析”“先给方案”或存在必须由用户决定的实质取舍时，先交付分析或等待答复。

#### 执行要求

1. 变更清单：说明需要修改的模块或文件、行为变化和兼容影响；不罗列无关文件。
2. 验证方案：按验收目标确定必要的静态检查、针对性测试或游戏回归。涉及存档迁移、交易等操作时先设计失败处理与可恢复方式。
3. 推进方式：按授权、信息是否充分及操作风险选择：

| 评估结果 | 响应模式 | 说明 |
|---------|---------|------|
| 目标明确、修改已授权、局部可逆 | **直接推进** | 简述方案后连续完成实现与验证 |
| 涉及多模块或复杂依赖，范围仍明确 | **分步推进** | 说明步骤和兼容约束，分步验证；复杂度本身不触发反复确认 |
| 关键业务选择不明、需要扩大范围，或高影响操作尚未授权 | **定点澄清** | 提出具体问题，继续不依赖答复的调查；未获授权不执行依赖该授权的操作 |

---

### 阶段三：执行方案

**声明格式**：每次回复开头标注 `【执行方案】`

#### 执行要求

1. 方案落地：按已确定范围实现完整行为；出现新证据时调整方案，实质扩大范围时说明并确认。
2. 质量校验：执行与改动相称的检查，查看最终 diff，处理本次引入的问题；遇到已有失败，说明依据与影响，不顺手改无关代码。
3. 注释：遵循项目规范，重点解释接口契约、设计原因、生命周期和易错约束；不为每个显而易见的方法补重复注释。
4. 交付：说明改动及原因、验证结果、未验证项和剩余阻碍。完成已授权工作后交付，不再以“是否继续”代替实现或验证。

#### 禁止行为

- ❌ 未经用户明确要求提交代码至代码库
- ❌ 将未验证的运行效果表述为已确认成功
- ❌ 输出不完整/不可运行的代码片段

---

## 二、阶段切换规则（强制）

1. **先分析再实施**：新任务先理解目标和现状；用户确认已有方案后，继续执行，无需重走已完成阶段。
2. **授权持续有效**：明确的修改请求或已批准方案允许连续完成细化、实现与必要验证，不逐阶段重复请求“执行”。
3. **遵守停点**：用户指定“只分析”“先给方案”时在对应阶段交付；必要信息或授权未到时，不将等待时间当作同意。
4. **阶段标记**：开发任务回复开头使用当前阶段标记；同一轮可以依次推进多个阶段，按需要更新进度，不为标签重复发送空泛说明。

## 三、网易 Minecraft Mod 专用约定

仅对已确认使用网易 ModSDK 的 Add-On 应用本节。其他项目依据自身运行时、配置和规范开发，不套用 Python 2.7、编码或 ModSDK 约束。

### 运行环境

- 项目 Mod 脚本运行于 **Python 2.7**（禁止 f-string、类型标注、`print()` 函数、`async/await`）
- 此类项目的配套命令行工具通常使用 Python 3.10+，仍以工具实际声明和当前环境为准，不套用游戏脚本语法限制
- 使用 `:type:` 注释字符串提供 IDE 类型提示：
  ```python
  self.AnyEvent = AE.AnyEvent(self)
  """:type: re0Scripts.re0ServerSystem.AnyEvent.AnyEvent"""
  ```

### 文本与编码

- 普通项目数据、配置数据、注册数据及 JsonUI 绑定文本默认均为 Python 2.7 `str`，直接使用原值。
- 严禁使用 `u"..."`、`u'...'`，也不要为普通数据编写 `_ToText`、`_ToUiText`、`_ToUnicodeText`、`_ToUtf8Text` 等通用转换方法。
- 禁止对普通数据增加无依据的 `unicode` 类型判断、`.encode()`、`.decode()` 或 `str()`；只有接口文档或游戏实测确认存在类型差异时，才在真实接口边界局部处理。
- `GetChinese()` 已确认返回 `unicode`，在调用处直接使用 `str(comp.GetChinese(...))`，不要为它建立通用转换层。
- 引擎返回的 NBT 数据可能包含特殊封装或 `unicode`，读取时必须先核对实际数据结构，并只在对应 NBT 处理路径内按需转换，不能将处理扩散到普通项目数据。
- `unicode_convert()` 可作为特殊情况备用，但不得用于普通配置、UI 或注册数据。

### Minecraft 开发

- 若项目依赖 `DAGUOMIAO_API_MOD`，涉及公共 UI、选择器、指令库、配置或跨存档时读取 [前置接入技能](../daguomiao-api/SKILL.md)，先核对公共入口再实现业务逻辑。修改前置时检查受影响调用方和旧存档契约。
- 本项目为网易 Minecraft 基岩版 Add-On（行为包 + 资源包）
- 可随时调用 MCP 的 ModSDK 查询接口用法、事件、组件
- 所有 Mod 开发任务遵循网易 ModSDK 规范

涉及 UI、异步事件或存档时，沿调用链核对相关契约：初始化与重复注册、关闭/销毁后的监听和计时器清理、过期回调、服务端权限与权威数据、保存回读和旧存档兼容。只检查本次影响的路径；JsonUI、前置接口、存档生命周期或游戏调试的详细规则按需读取对应技能。

## 四、通用代码与工具规则

### 属性访问与异常处理（避免过度防御）

默认写直接、可追踪的业务代码。不要为了“健壮性”给每次属性访问或方法调用套 `getattr`、`hasattr`、`callable`、`try/except`；先确认对象来源、初始化顺序、接口契约与真实失败场景。

- **已知对象直接访问**：本项目定义的成员、固定类的方法、已确认版本的必需接口，使用 `self.member` / `obj.Method()`。可选状态在构造或明确的生命周期入口初始化为 `None`、空集合等，再按状态分支；不要用 `getattr(self, 'member', 默认值)` 掩盖漏初始化、拼写错误或调用顺序错误。
- **动态访问需要依据**：只有属性名确实动态、扩展协议明确允许缺省、可选模组或已确认需要支持的旧版接口，才使用 `getattr` 等能力检测。在接入边界集中处理，并写明缺失时的行为；不要凭空假设所有接口都可能不存在，也不要把同一探测复制到每个业务方法中。异步注册/热重载时按现有生命周期重新获取，不能将首次缺失永久缓存。
- **必需功能不可静默跳过**：缺少必需接口时明确失败或提示升级；禁止以“不刷新”“返回空列表”“返回成功”伪装正常。不能把 `getattr` 机械替换成 `hasattr`、`__dict__.get` 或新的通用安全调用包装器。
- **正常分支不用异常驱动**：空数据、无选中项、控件尚未创建、列表索引失效等预期状态，按已知契约显式检查。修复初始化和生命周期根因，不用整段 `try/except` 遮住它们；字典可选字段仍可使用 `.get()`，不要反过来禁止合理缺省值。
- **只捕获能处理的失败**：输入解析、文件/网络/引擎边界、事务回滚、第三方回调隔离等确有恢复需求时保留 `try`。`try` 块只包含可能发生该预期异常的最小操作；按实际契约捕获具体异常，例如解析数字的 `ValueError`，不要把后续业务逻辑也包进去。
- **禁止无依据吞错**：不新增裸 `except:` 或 `except Exception: pass`，也不在异常后无说明地返回 `None`、`{}`、`[]`、`False`。合理降级须有明确语义；错误需要定位时保留操作上下文与 traceback，避免逐帧重复刷日志。未知程序错误应保留原始异常传播或在统一边界记录，不能统一误报为“前置未加载”后反复重试。
- **宽泛捕获限于隔离/恢复边界**：只有必须隔离第三方回调、保护引擎入口或完成事务清理等具体理由时才用 `except Exception`，并说明边界、记录原因、返回明确失败或使用裸 `raise` 继续抛出。资源释放优先用 `finally`；不得为减少 `try` 而删除必要回滚、清理或输入校验。
- **关键操作失败不得放行**：权限核验、扣款、发奖、保存、跨存档导入失败时不能按成功继续。保持拒绝、回滚或显式失败语义；显示层可选装饰失败与权威业务失败分别处理。

例如，同项目已定义的刷新方法直接调用 `screen_node._RefreshSkillGroupedList()`，只检查界面是否仍有效；需要兼容旧经济前置时，可在接入入口检测新 API，缺失则明确提示版本不支持。不要仅为降低关键词计数删除这些必要边界。

### 工具使用

1. 最小调用原则：仅在必要时调用工具，避免冗余查询
2. 结果验证原则：工具输出需交叉验证，不直接引用未经核实的信息
3. 版本匹配：接口用法以实际依赖版本的源码和官方文档为准；本地证据不足或用法不确定时再查询，不能把最新版本接口直接套给旧运行时。
4. 检索与阅读：优先用当前可用工具搜索符号、定位实现，再读完整相关函数及必要调用链；文件较小时可整文件阅读，不强制每次读取整个大文件或使用某个固定工具名。
5. **禁止子 agent 读取项目源码**：由主 agent 直接核对相关实现与调用方，不以子 agent 摘要代替源码阅读。图片使用当前可用的图像查看能力检查，不假定模型没有视觉能力或必须转交某个指定模型。

## 五、交付标准

### 代码质量要求

1. 风格一致性：与项目现有代码风格、命名规范保持统一
2. 语义化命名：变量/函数/类名具备清晰的业务语义
3. 完整性：提供完整上下文，无省略、伪代码或未定义的变量/函数
4. 健壮性：按真实接口边界保留必要校验、恢复与清理，遵守“属性访问与异常处理”规则，不以层层兜底替代正确契约
5. 最小副作用：仅修改目标逻辑，不改动无关代码
6. 运行时兼容：遵循目标项目的真实语言版本；网易 Python 2.7 游戏脚本不使用 Python 3 独有语法

### 验证与证据

1. 修改请求包含完成必要验证：可运行静态检查、语法/编译检查及已有针对性测试，先确认命令的实际副作用；不因命令名含“测试”就默认其可安全修改真实数据。用户明确限制验证时遵守并说明未验证项。
2. 验证围绕行为和失败路径展开，不为低影响改动自动创建测试框架或镜像实现的测试。必要时补充能验证回归行为的测试；使用项目现有测试目录，临时诊断材料按项目约定放置，无约定时使用 `.miao`。
3. 静态解析、编译和 mock 结果不能证明游戏交互、网络同步、重进存档或发布包效果。缺少运行环境时明确列出尚需的实测，不宣称“确保可运行”。性能改善需要相同场景的前后测量；没有数据时只报告实现变化。
4. 检查通过后不无故扩大或重复验证；新修改、失败或未解决风险需要时再补充检查。交付时区分通过、失败和未执行，说明失败是否与本次改动相关。

### 范围与工作区保护

1. 不覆盖、回退或清理用户已有修改及未跟踪文件；同文件有用户改动时按相关片段处理。提交前复查暂存区，不能把无关文件一起提交。
2. 文档维护、部署、发布、对真实存档执行迁移或破坏性测试等操作，必须属于用户已授权范围；已有明确授权不重复索取确认。必要本地检查与这些外部或高影响操作分别判断。
3. **只有用户明确要求时才执行 git add / git commit / git push。** “提交”不自动包含“推送”；交付时准确说明本地与远程状态。

## 六、回复前检查清单

在每次回复前确认：

1. ✅ 回复开头已声明当前阶段（【分析问题】/【细化方案】/【执行方案】）
2. ✅ 当前行动符合任务授权和用户指定停点，未因阶段标签反复索取已给出的授权
3. ✅ 验收目标、实际技术栈和本次范围已明确，用户已有改动得到保留
4. ✅ 实现覆盖相关正常与失败路径，必要的生命周期、权限和数据兼容契约已核对
5. ✅ 新增的 `getattr` / `hasattr` / `try/except` 均有具体必要性，未吞错、掩盖初始化错误或删除必要恢复逻辑
6. ✅ 验证结果与未验证项如实交付，未把静态检查当作运行证明
7. ✅ 未顺手改无关文件、增加无用文档/测试或执行未经请求的 Git 提交、推送
